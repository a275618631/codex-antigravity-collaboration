--- layout: doc title: "狀態與路線圖" source_md: "STATUS_AND_ROADMAP.md" --- {% capture zh %} # 狀態與路線圖 本頁整理目前已完成、部分完成、規劃中與探索中的項目。狀態以可直接驗證的實作與測試結果為準；尚未完整驗證的能力會明確標示，不提前視為已完成。 ## 狀態定義 - **已實作**：已有可執行實作，並完成直接驗證。 - **部分完成**：主要方向與實作已存在，但仍有同步、收斂或驗證工作尚未完成。 - **已規劃**：架構與做法已定義，尚未列入已完成能力。 - **探索中**：可能的後續方向，是否導入仍取決於實際需求。 ## 目前實作狀態 | 項目 | 狀態 | 說明 | |---|---|---| | Codex 唯讀前置檢查 | **已實作** | 前置檢查流程已可使用。 | | Codex 低摩擦核准／沙箱基線 | **已實作** | 權限與沙箱基線已套用並驗證。 | | Antigravity 權限基線 | **已實作** | 已使用細粒度允許／詢問／拒絕設定。 | | Codex → Antigravity 基本橋接測試 | **已實作** | 唯讀基本橋接測試已通過。 | | 共用 Task / Result Packet（任務／結果格式） | **已實作** | 已用於目前協作流程。 | | One-Hop Guard（單次跨平台轉交限制） | **已實作** | 已納入協作流程；接收端仍可使用自己的內部 Agent／Subagent。 | | Shared Workspace（共享工作區） | **已使用** | GitHub／Google Drive 用於保存任務、結果、文件、PR 與審查紀錄；它是持久工作區，不是即時訊息匯流排。 | | 唯讀 Debate（雙方審查／辯論） | **已實作** | 目前流程上限為兩輪。 | | 平台原生平行 Agent | **已實作／原生能力** | 直接使用平台本身能力，不由本專案重做。 | | Shared Skill（共用技能）唯一來源 | **部分完成** | 唯一來源與同步一致性仍待完成最終收斂。 | | 本地模型雙向溝通 | **實驗中** | 已完成獨立測試，尚未整合到隱私感知信任模型。 | ## Shared Skills（共用技能） 目前已建立跨 Runtime 共用 Skill 的方向，但唯一來源與同步一致性尚未完成最終驗證，因此維持在「部分完成」。 目標架構是： > **一個可攜方法 → 一個唯一來源 → 只有必要的平台差異才使用薄 Adapter（轉接層）。** 升級為「已實作」前，仍需完成： - Duplicate / drift scan（重複／漂移掃描）； - 確認唯一來源； - 重新驗證各 Runtime 的 Adapter 與載入結果。 ## 近期規劃 ### 隱私感知的本地／雲端分流 — 已規劃 預計採用小型、可驗證的處理路徑： 1. 確定性的 Secret / PII（祕密／個人可識別資訊）偵測； 2. 本地分類； 3. Context（上下文）最小化； 4. 對允許類別進行可逆假名化； 5. 本地還原； 6. 外洩測試。 優先使用成熟偵測元件與薄型本地 Policy layer（政策層），避免為這項需求新增不必要的大型資安 Framework。 ### 本地模型作為私密／離線處理路徑 — 已規劃整合 本地模型預計支援： - Restricted（限制）或離線任務； - 網路受限環境； - 敏感內容的語意分類； - 特定低風險自動化。 本地模型用來補充確定性 Policy（政策），而不是取代它。 ## 探索中的方向 ### 跨電腦協調 先從多台電腦共用 Workspace（工作區）開始。 只有任務真的需要明確的跨主機 request / result（請求／結果）傳輸時，才進入專門的 Agent interoperability layer（Agent 互通層）。 [A2A](https://github.com/a2aproject/A2A) 是現成的開放標準；若未來需要更明確的跨 Runtime 或跨主機協調，可優先評估是否適用。 ### 薄型 Broker（任務仲介服務） Broker **不是目前架構的一部分**。 只有實際出現以下需求時才考慮引入： - Lease（租約）； - Heartbeat / Liveness（心跳／存活確認）； - Retry（失敗重試）； - Distributed task state（分散式任務狀態）； - Concurrency ownership（併發寫入所有權）； - Real-time scheduling（即時排程）。 ## 升級為「已實作」的條件 一個路線圖項目要標記為 **已實作**，至少需要： 1. 有可以執行或直接觀察的實作； 2. 已進行 End-to-End（端到端）測試； 3. 重要失敗案例有被測試； 4. Security / Permission（資安／權限）行為有文件； 5. 有 Rollback（回復）或安全停用方式； 6. 公開說明與實際能力一致。 ## 架構原則 新增基礎設施應由實際協調需求驅動。若現有平台原生能力、共享工作區與薄型橋接已能可靠完成工作，就不額外增加新的中央服務或長期依賴。 {% endcapture %} {{ zh | markdownify }}
